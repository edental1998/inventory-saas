# Inventory SaaS — ניהול מלאי לרשתות מזון

פלטפורמת ניהול מלאי רב-מותגית לרשתות בייקרי, בתי קפה ופטיסרי. ראו [`ARCHITECTURE.md`](./ARCHITECTURE.md) להסבר המלא על מודל הנתונים, התפקידים, מנוע ה-theming, ארכיטקטורת ה-i18n, ופירוט השלבים (Phases).

## מה עובד עכשיו (Phase 0 + חלק מ-Phase 1 + Phase 2 מלא + Phase 3 בהיקף מצומצם)

זו כבר לא רק הדגמה ויזואלית — יש כאן מערכת עם מסד נתונים אמיתי והתחברות אמיתית: התחברות עם אימייל/סיסמה (מוצפנת עם bcrypt), עוגיית session חתומה, שלושה דשבורדים מוגנים לפי תפקיד (הנהלה/מנהל סניף/עובד) שכל אחד מהם רואה רק את מה שמותר לו, וסימון משימה כ"בוצעה" שבאמת נשמר במסד הנתונים ולא נעלם ברענון. שני מותגי דמו ("מאפיית השיבולת" ו-"קפה מרידיאן") מציגים כל אחד את הנתונים האמיתיים שלו — סניפים, משימות, מכירות והתראות תוקף — עם עיצוב שונה לגמרי, ותמיכה מלאה בעברית (RTL) ואנגלית (LTR) עם מעבר חי בין השפות.

בנוסף, עובד/מנהל סניף יכולים לגשת ל"צלם מוצר" בתפריט הצד ולתעד מוצר **בלי קוד פריט בכלל**, בשלושה מסכים (טאבים): "הגעה לחנות", "זריקה/סיום" ו"עדכון כמות". בהגעה ובזריקה מצלמים את המוצר — המערכת מנסה לזהות לבד איזה מוצר זה בעזרת Claude (דורש `ANTHROPIC_API_KEY` משלכם ב-`.env`, ראו בהמשך איך מחברים), פותחת אוטומטית אצווה עם תאריך תפוגה מחושב בהגעה, ומקזזת בדיוק את הכמות שהוזנה מהאצווה/האצוות הפעילות בזריקה (ראו בהמשך "מעקב כמות חלקי"). בלי מפתח AI מוגדר (או כשה-AI לא בטוח מספיק) המערכת פשוט מציגה לעובד רשימת בחירה קצרה במקום לנחש — הכל עדיין עובד, רק בלי הזיהוי האוטומטי. אם על המוצר יש מדבקת תוקף מודבקת, אותה קריאה בדיוק מנסה גם לקרוא ממנה תאריך — אבל התאריך הזה **תמיד** עובר דרך מסך אישור/עריכה של העובד לפני שהוא נשמר בפועל, גם אם ה-AI היה בטוח לגמרי; זו החלטה מכוונת, לא מגבלה טכנית (פירוט ב-ARCHITECTURE.md).

הטאב השלישי, "עדכון כמות", הוא **לא** צילום — הוא רק מעדכן איפה כמות שכבר נקלטה נמצאת עכשיו (העברה למדף, כניסה למקפיא, או הוצאה מהמקפיא למדף), בלי מצלמה ובלי AI, כי אלה פעולות שקורות הרבה פעמים ביום ולא הגיוני לצלם בכל פעם. פירוט מלא במדור "מעקב כמות חלקי" למטה.

מסך "מכירות" חדש (בתפריט הצד, גם בדשבורד הסניף וגם בדשבורד ההנהלה) מציג מגמת מכירות יומית, מוצרים מובילים, פחת מול מכירות לכל מוצר, טבלת "אומדן מכירה מול מכירות בפועל" ופירוט סיבות זריקה — כולם מנתונים אמיתיים. אפשר גם לייבא נתוני מכירות מקובץ CSV. **לגבי חיבור ישיר לקופה (POS):** זה לא מומש, כי בשלב הזה עדיין לא נבחרה מערכת קופה קבועה — בלי לדעת מול איזו מערכת ספציפית להתחבר, אין API אמיתי לכתוב מולו. הייבוא מ-CSV הוא הפתרון המעשי להיום, ונבנה כך שמחר, כשתיבחר קופה, יתווסף לו "מתאם" חדש בלי לגעת בשאר המערכת (פירוט ב-ARCHITECTURE.md → "תכנון Phase 3").

## איך מחברים מפתח AI אמיתי (Anthropic)

1. נכנסים ל-[console.anthropic.com](https://console.anthropic.com), יוצרים חשבון (אם אין) ומייצרים API key חדש.
2. פותחים את קובץ `.env` בשורש הפרויקט (אם אין — מעתיקים מ-`.env.example`) ומוסיפים שורה: `ANTHROPIC_API_KEY="sk-ant-..."` (המפתח האמיתי שקיבלתם).
3. מריצים מחדש את השרת (`npm run dev` או `npm run build && npm run start`) כדי שהמשתנה החדש ייטען.
4. זהו — "צלם מוצר" יתחיל לזהות מוצרים ומדבקות תוקף אוטומטית. בלי המפתח הזה, אותו מסך ממשיך לעבוד במלואו, רק עם בחירה ידנית של המוצר במקום זיהוי אוטומטי.

אפשר גם לכוון את המודל הספציפי דרך `ANTHROPIC_VISION_MODEL` (ברירת מחדל: מודל קטן ומהיר, `claude-haiku-4-5`), ואת `ANTHROPIC_BASE_URL` אם יש proxy ארגוני — שניהם מתועדים ב-`.env.example`.

## למה SQL ידני ולא Prisma Client, בינתיים

שכבת הנתונים (`src/lib/data/*.ts`) כותבת שאילתות SQL ישירות דרך ה-driver הרשמי `pg`, ולא דרך Prisma Client — למרות ש-`prisma/schema.prisma` הוא עדיין המקור האמיתי (source of truth) של המודל, ו-`prisma/schema.sql` הוא ה-DDL הידני שמשקף אותו 1:1. הסיבה: בסביבת הענן שבה נכתב הקוד הזה, הגישה לשרת ההפצה של קובץ ה-engine של Prisma (`binaries.prisma.sh`) הייתה חסומה ברמת הרשת, כך ש-`npx prisma generate` לא הצליח לרוץ שם (למרות כמה ניסיונות עוקפים אמיתיים — driver adapters, חבילות ה-wasm הרשמיות דרך npm, וכו'). ב-**כל סביבה רגילה** (המחשב שלך, GitHub Actions, Vercel) `npx prisma generate` יעבוד מיידית בלי שום שינוי קוד, ואפשר יהיה לעבור בהדרגה משכבת ה-SQL הידנית ל-Prisma Client המלא, בלי לגעת בסכמה עצמה. עד אז, שכבת ה-`pg` הנוכחית היא קוד production-grade לגיטימי (הרבה מערכות אמיתיות בוחרות ב-SQL מפורש במקום ORM בכוונה), לא "טלאי זמני מפוקפק".

## מה עדיין לא ממומש

תמונות רפרנס אמיתיות למוצרי הדמו (הקוד תומך בזה, פשוט ה-seed לא כולל תמונות עדיין). אין עדיין SSO/ספקי התחברות חיצוניים, ואין מסך ניהול-מותג ויזואלי (שינוי צבעים דרך קובץ/DB ישירות בינתיים, לא דרך UI). כל אלה מפורטים בטבלת ה-Phases ב-ARCHITECTURE.md.

## איך "צלם מוצר" עובד בפועל

1. עובד/מנהל סניף נכנסים ל"צלם מוצר" בתפריט, ובוחרים אחד משלושה טאבים: "הגעה לחנות", "זריקה/סיום" או "עדכון כמות".
2. **הגעה לחנות:** מצלמים (או בוחרים קובץ תמונה) ומזינים כמה יחידות הגיעו.
3. **זריקה/סיום:** מצלמים את המוצר, מזינים כמה יחידות **בפועל** נזרקו (לא בהכרח כל מה שנשאר מהאצווה), ובוחרים סיבה מרשימה סגורה: פג תוקף / מראה-איכות ירודה / מזיקים / **חשד לצריכה-נטילה לא מתועדת על ידי עובד** / אחר. הסיבה חובה — אי אפשר לשלוח בלעדיה.
4. **עדכון כמות:** בוחרים מוצר מרשימה, בוחרים יעד (העברה למדף / כניסה למקפיא / הוצאה מהמקפיא למדף) ומזינים כמות. אין כאן מצלמה בכלל — זו פעולה נפרדת ומהירה במכוון (ראו "מעקב כמות חלקי" למטה).
5. **עם `ANTHROPIC_API_KEY` מוגדר ב-`.env`:** בהגעה ובזריקה, התמונה נשלחת ל-Claude יחד עם קטלוג המוצרים של הארגון. אם הביטחון גבוה מספיק (85%+) — הפעולה מתבצעת מיד, בלי אינטראקציה נוספת.
6. **בלי מפתח, או כשה-AI לא בטוח:** מוצג לעובד מסך "איזה מוצר זה?" עם עד 3 ניחושים (אם היו) ואפשרות לפתוח את כל הקטלוג — נגיעה אחת וזהו.
7. בדיקה עצמאית: כל מסלול נבדק בפועל מול ה-DB (Playwright + שאילתת pg ישירה) — כולל חישוב תאריך התפוגה, הקצאת FIFO רב-אצוות בזריקה/עדכון כמות, ואי-חסימה כשהכמות שהוזנה גדולה מהמלאי הרשום.

התמונות שנשמרות נמצאות תחת `public/uploads/<ארגון>/<סניף>/...` — פתרון מקומי שמספיק לפיתוח, ראו ARCHITECTURE.md לגבי המעבר לאחסון אובייקטים אמיתי לפני production.

## מעקב כמות חלקי — התשובה לשאלה "מה קרה לכמות שלא נזרקה?"

השאלה שהובילה להרחבה הזו: אם מעלים למדף כמות אחת ואז זורקים כמות אחרת, האם ההפרש הוא בהכרח מה שנמכר? **התשובה: לא בהכרח** — ולכן הבנייה כאן היא שילוב של שני כלים נפרדים, לא ניחוש אחד:

1. **מעקב כמות אמיתי לכל אצווה.** כל אצווה (`inventory_batches`) שומרת כמה יחידות במדף, כמה במקפיא, וכמה נזרקו עד כה — ומתעדכנת בעסקת DB אחת (transaction) בכל פעולה. אפשר לזרוק חלק מאצווה כמה פעמים לאורך זמן (למשל 2 יחידות היום כי נראו לא טוב, ועוד 3 מחר כי פג תוקף), ולתעד כל אירוע בנפרד עם הסיבה שלו — האצווה נסגרת אוטומטית רק כשכל הכמות שהגיעה בה כוסתה במדף/מקפיא/זריקה. הקצאה בין אצוות היא FIFO (הישנה ביותר קודם), ויכולה לפרוש על פני כמה אצוות אם אצווה אחת לא מספיקה. אם הכמות שהוזנה גדולה מהמלאי הפעיל הרשום, המערכת **לא חוסמת** את הפעולה (כי לתעד את מה שקרה בפועל חשוב יותר מלאכוף ספר חשבונות מושלם) — היא מקצה כמה שיש ומציגה אזהרה עם הכמות שלא שויכה.
2. **סיבת זריקה חובה, כולל קטגוריה ל"חשד לצריכה לא מתועדת".** בכל זריקה נבחרת סיבה, ואחת מהן מיועדת בדיוק למקרה שביקשתם: חשד שעובד לוקח/אוכל מוצר בלי לתעד זריקה אמיתית. במסך "מכירות" יש דוח "פירוט סיבות זריקה" שמרכז את כל הסיבות לתקופה, עם הדגשה חזותית לסיבה הזו — כך שאפשר לראות במבט אחד אם היא בכלל מופיעה, ובאיזו תדירות.
3. **"אומדן מכירה" מול מכירות בפועל — תמיד זה לצד זה, אף פעם לא מוצג כמכירה אמיתית.** באותו מסך "מכירות" יש טבלה שמחשבת, לכל מוצר, "אומדן" = כמות שעלתה למדף פחות כמות שנזרקה (מבוסס על תיעוד הצילומים/עדכוני הכמות), ומציגה אותו **לצד** המכירות שדווחו בפועל (מ-`sale_records`, שמגיעות מייבוא CSV או קופה בעתיד) — עם עמודת "פער" ביניהם. פער חיובי גדול אומר "כמות גדולה עלתה למדף, לא נזרקה, אבל גם לא נרשמה כמכירה" — יכול להיות מכירה שלא דווחה, טעות תיעוד, או צריכה לא מתועדת. זה כלי בקרה לאיתור פערים, **לא** נתון מכירה בעצמו — ולכן הוא תמיד מסומן בבירור ומוצג בנפרד מהמכירות האמיתיות, כדי לא לחזור על הטעות של להציג הערכה כאילו היא עובדה.

פירוט טכני מלא (הקצאת ה-FIFO הרב-אצוותי, הקבועים הרצים, ולמה ה"אומדן" הוא מכוון כך שלא ניתן להתבלבל בינו לבין מכירה אמיתית) נמצא ב-ARCHITECTURE.md → "הרחבה: תנועות מלאי חלקיות וסיבת זריקה".

## איך "מכירות" עובד בפועל

1. מנהל סניף נכנס ל"מכירות" בתפריט, ורואה מיד מגמת מכירות (30 ימים), מוצרים מובילים, ופחת מול מכירות — מנתוני `sale_records` ו-`stock_movements` האמיתיים בסניף שלו. מנהל רשת רואה את אותם גרפים, מצטברים על כל הסניפים יחד.
2. מתחת לגרפים מופיעות שתי תצוגות נוספות מ"מעקב כמות חלקי" (ראו למעלה): טבלת "אומדן מכירה מול מכירות בפועל" לכל מוצר, ורשימת "פירוט סיבות זריקה" לתקופה — שתיהן זמינות בשני הדשבורדים.
3. לייבוא מכירות: בוחרים קובץ CSV עם עמודות `date,product,quantity` (ו-`revenue` אופציונלי; תאריך בפורמט `YYYY-MM-DD` או `DD/MM/YYYY`) ולוחצים "ייבוא". המערכת משייכת כל שורה למוצר בקטלוג לפי שם, ומדווחת בדיוק אילו שורות דולגו ומדוע (מוצר לא נמצא, תאריך לא תקין וכו') כדי שאפשר יהיה לתקן ולנסות שוב.
4. אין עדיין חיבור חי לקופה — ראו ARCHITECTURE.md → "תכנון Phase 3" להסבר המלא למה, ומה התוכנית להוספה עתידית בלי לשנות את שאר המערכת.

## הוספת מותג/רשת חדשה

להוסיף רשומה בטבלת `organizations` + `brand_themes` (ידנית או דרך `prisma/seed.ts` כדוגמה), ולתת למשתמשים החדשים להתחבר — הם יראו אוטומטית את המותג של הארגון שלהם. אין צורך לגעת בשום קובץ קוד; כל הרכיבים בממשק תלויים רק בטיפוס `BrandTheme` (`src/lib/themes/types.ts`), לא בערכים ספציפיים.
